# Promoted technical manager becomes execution bottleneck

## Short answer

This draft case study shows how a promoted technical manager can become an execution bottleneck when the operating model isn't explicit, and how The Push framework provides the path forward.

- Show the problem clearly—isolation, implicit rules, bottleneck formation.

## Content

### Situation

A strong technical engineer is promoted to Engineering Manager for the first time. They have a reputation for high-quality work, deep technical knowledge, and ability to solve hard problems. They earned the promotion through technical excellence and delivery speed.

In their first weeks as manager, they maintain the same approach they used as a tech lead: stay close to technical decisions, review code carefully, ensure quality, keep delivery moving. They take on all the manager responsibilities—1:1s, hiring, planning—while still staying deeply involved in the team's technical work.

### Tension

Three months in, the pattern becomes clear: the team waits for the manager's input more than before. Decisions that used to be made by the tech lead now wait for the manager's approval. Code review cycles have slowed because the manager reviews most PRs. Architectural decisions require the manager's input. Feature priorities depend on the manager's judgment.

The manager is working long hours trying to do both jobs well: be a technical authority and be a manager. The team is frustrated—everything takes longer, and they feel less autonomous. The manager is frustrated—there's always more to review, more to approve, more to think about.

What happened? The manager brought the execution mindset into a management role. As a tech lead, they could solve problems directly and stay close to the work. As a manager, that approach becomes a bottleneck.

The root cause: the operating model is implicit, not explicit. The team doesn't understand the manager's decision rules, review standards, or delegation boundaries. So they default to asking the manager. The manager doesn't have a published framework for what they will and won't be involved in. So they end up involved in everything.

### Intervention

The Push framework addresses this by moving from Invisible Executor to Trusted Operator:

**Invisible Executor:** The manager executes well (strong technical and delivery output) but operates invisibly (the team doesn't understand the decision framework, and the manager becomes the bottleneck).

**Trusted Operator:** The manager makes the operating model explicit—who decides what, what standards apply, what can be delegated—so the team understands the system and can operate without constant escalation.

The intervention includes:

1. **Making decision authority explicit:** The manager documents what types of decisions they make personally, what they delegate, and what require team input. For example:
   - Team member decides: code style, non-breaking refactoring, documentation
   - Team lead decides: architecture within approved patterns, which features to schedule
   - Manager decides: hiring, promotion, strategic direction, major architecture changes
   
2. **Publishing review standards:** The manager defines what good code review looks like, what's non-negotiable, and what's optional. For example:
   - All code should be readable and maintainable.
   - Architectural changes need review; style changes don't.
   - Performance-critical code needs thorough testing.
   
3. **Setting delegation boundaries:** The manager clarifies what code changes can be approved by team members, what require team lead approval, and what require manager review. For example:
   - Team members can approve documentation updates and test improvements.
   - Team lead can approve routine features and non-breaking refactorings.
   - Manager reviews major architectural changes and breaking changes.

4. **Communicating the framework:** The manager shares this with the team, explains the reasoning, and makes it a reference point for decisions.

Expected direction (pending evidence):
- Decision latency decreases because team members can make decisions at the right level without escalation.
- Code review cycles improve because standards are clear.

- Team autonomy improves because the rules are clear.

But these outcomes depend on the specific context, the organization's culture, and how well the operating system is implemented. They should not be claimed without evidence.
